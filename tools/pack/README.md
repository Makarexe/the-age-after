# tools/pack — манифест сборки

Запускается **только на ПК владельца**: читает инстанс CurseForge и публикует то, что скачивает лаунчер.

## Что делает

- Моды, ресурспаки и шейдеры из CurseForge попадают в `manifest.json` ссылками на их CDN (`edge.forgecdn.net`): мы их не перераздаём. sha1 проверяется по файлу на диске.
- Свои jar (которых нет в `minecraftinstance.json`) и jar, изменённые локально, загружаются в GitHub Release `pack-latest`.
- `config/`, `defaultconfigs/`, `kubejs/` и `options.txt` упаковываются в `config.zip` (список — `pack.json`). `options.txt` лаунчер ставит только при первой установке.
- `*.disabled` пропускаются.
- `sides.json`: `serverOnly` — моды только для сервера (игрокам не уходят), `clientOnly` — только для клиента (не попадают в `server-mods.txt`). Шаблоны имён: `*` — что угодно.
- Версия сборки — `YYYY.MM.DD-N`, N растёт, если в этот день уже публиковали.

## Как запустить

Нужны Node 22+ и [GitHub CLI](https://cli.github.com/) (`gh auth login` один раз).

```powershell
cd tools\pack
node build-pack.mjs --instance "C:\Users\<вы>\curseforge\minecraft\Instances\<инстанс>"            # собрать и посмотреть
node build-pack.mjs --instance "C:\Users\<вы>\curseforge\minecraft\Instances\<инстанс>" --upload   # опубликовать
```

Скрипт покажет, что изменилось относительно опубликованной сборки, и предупреждения. Результат — в `tools/pack/out/` (в git не попадает):

- `manifest.json` — для лаунчера;
- `assets/` — что уходит в Release;
- `server-mods.txt` — какие jar должны лежать в `mods/` сервера.

`--check-urls` дополнительно проверит, что все ссылки CurseForge отвечают.

### Поменять только моды, не трогая конфиги

```powershell
node build-pack.mjs --instance "<папка инстанса>" --upload --mods-only
```

Моды публикуются заново, а `config.zip` остаётся тем, что уже опубликован, — у игроков конфиги не меняются, их личные правки в `config/` сохраняются. Если для нового мода нужны ваши настройки (а не те, что мод создаст сам), опубликуйте без `--mods-only`.

Release `pack-latest` создаётся как pre-release, чтобы не стать «последним релизом»: из последнего релиза лаунчер берёт свои обновления.

## Формат manifest.json

```json
{
  "formatVersion": 1,
  "packVersion": "2026.10.09-1",
  "minecraft": "1.21.1",
  "neoforge": "21.1.262",
  "files": [{ "path": "mods/x.jar", "sha1": "…", "size": 123, "url": "https://edge.forgecdn.net/…" }],
  "overrides": { "url": "…/config.zip", "sha1": "…", "size": 456, "files": 789 },
  "managedDirs": ["mods"],
  "firstInstallOnly": ["options.txt"]
}
```

Лаунчер скачивает `files` и проверяет sha1, удаляет из `managedDirs` всё, чего нет в `files`, и распаковывает `overrides` поверх папки игры, только когда изменился сам `config.zip` (его sha1) или игрок нажал «Проверить файлы». Файлы из `firstInstallOnly` ставятся, только если их ещё нет.

### Выложить только часть конфигов

Обычная публикация кладёт в `config.zip` **все** конфиги, и при смене архива они перезаписывают конфиги игроков. Чтобы выкатить только нужные файлы:

```powershell
node build-pack.mjs --instance "<папка инстанса>" --configs "config/analogaudio/**"          # сухой прогон: покажет список
node build-pack.mjs --instance "<папка инстанса>" --configs "config/analogaudio/**" --upload
```

Через запятую можно несколько шаблонов (`*` — внутри папки, `**` — через папки).
- `config.zip` остаётся тем, что уже опубликован. В Release добавляется маленький `config-patch.zip`, в нём **только** выбранные файлы (сухой прогон печатает их список, проверьте его до `--upload`); в манифесте это `overridesPatch`.
- Лаунчер с версии 0.1.16 применяет патч один раз поверх конфигов игрока; остальные конфиги и личные правки не тронуты. Новая установка получает `config.zip`, потом патч.
- Старые лаунчеры патч не знают и ничего не меняют: до обновления лаунчера изменение до них не дойдёт, но и лишнего не придёт.
- Патч один: следующий `--configs` заменяет предыдущий (список всех нужных файлов указывайте в одной команде). Обычная публикация без флагов патч убирает: все конфиги уже в новом `config.zip`. `--mods-only` патч сохраняет.
- «Проверить файлы» применяет `config.zip` и патч заново. `--configs` нельзя сочетать с `--mods-only`; нужна опубликованная сборка; шаблон без совпадений останавливает сборку.

### Установщик и библиотеки NeoForge

Кроме модов `build-pack` кладёт в Release `neoforge-<версия>-installer.jar` и `neoforge-libraries-<версия>.zip` (библиотеки установщика с `maven.neoforged.net`: ≈50 файлов, ≈17 МБ, sha1 каждого сверяется; библиотеки Mojang и патченные клиентские jar не включаются). В манифесте это `neoforgeInstaller` и `neoforgeLibraries`. Лаунчер сначала берёт их оттуда, потом с официального maven и зеркала BMCLAPI: так NeoForge ставится и там, где `maven.neoforged.net` недоступен. Файлы создаются один раз на версию NeoForge и переиспользуются.

### Опциональные моды

`optional-mods.json` попадает в `manifest.json` как `optionalMods`. Это клиентские моды, которые игрок сам включает галочками в лаунчере (вкладка «Настройки»); для входа на сервер они не нужны и в `server-mods.txt` не попадают. У записи: `id`, `name`, `description`, `files` (`path`, `sha1`, `size`, `url`), необязательные `requires` (id библиотек, ставятся вместе) и `library: true` (не показывать игроку). Ссылки — на Modrinth CDN, sha1 берётся из Modrinth API. Файл не должен совпадать по пути с модом сборки (проверяется при сборке). Чтобы добавить мод: найдите версию под `1.21.1` + `neoforge`, скачайте jar, сверьте sha1 и `META-INF/neoforge.mods.toml`.

Тесты: `npm test`.
